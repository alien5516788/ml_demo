Dynamic Programming (DP)
========================

Dynamic Programming is a MODEL-BASED family of RL algorithms.

The important idea is not how the model is implemented, but that the
algorithm has access to a model of the MDP:

M = S, A, P(s' | s, a), R(s, a, s'), gamma

Unlike Monte Carlo or TD methods, classical DP does not need to interact
with the real environment to evaluate a policy or improve it.

It can reason entirely from the mathematical model:

"If I am in state S and take action A, what can happen?"

P -> tells us what can happen
R -> tells us what we receive
gamma -> tells us how much future rewards matter


WHAT "MODEL-BASED" DOES NOT MEAN
--------------------------------

The model does NOT have to be manually hard-coded.

P and R could come from:

- hand-written rules
- lookup tables
- a simulator
- a mathematical equation
- a search procedure
- a learned model
- a neural network
- a combination of known and learned components

DP only cares that the required model information is available.

For example, instead of:

fn model(s, a, s_next) -> probability

we could have a learned model that predicts the possible next states.

The source of the model and the DP algorithm are separate concerns.

This is same with the Reward function, Policy function etc.

DOES DP LEARN?
-------------

Yes, but we must be precise about WHAT it learns.

In classical model-based DP, the environment model is already available.
DP does not discover the environment rules through interaction.

Instead, it computes quantities such as:

V(s)          -> value of a state
Q(s, a)       -> value of an action
pi(a | s)     -> an improved/derived policy

The value function is therefore not a description of the environment.
It is an estimate of how desirable states/actions are according to
the given MDP and policy/objective.


THE MODEL CAN BE LEARNED BEFORE DP
----------------------------------

There is an important distinction:

Classical DP:

    model is already available
        ↓
    DP plans using it


Model-based RL:

    interact with environment
        ↓
    learn/estimate a model
        ↓
    DP/planning using the learned model

The second case is still model-based RL.

Therefore, "DP does not learn the model" is more accurate than
"the model can never be learned."

DP simply assumes that the model is available when it performs its
planning/evaluation computation.


THE SAME IDEA APPLIES TO REWARD AND POLICY
------------------------------------------

The functions in an implementation are not sacred.

model()   -> implementation of P
reward()  -> implementation of R
policy()  -> implementation of pi

These could each be implemented in many different ways.

For example, a policy could be:

- hard-coded
- a lookup table
- generated by an algorithm
- represented by a neural network

A reward could be:

- a hand-written function
- a table
- derived from environment rules
- produced by a learned reward model

DP does not prescribe these implementation choices.


IMPORTANT ASSUMPTIONS
---------------------

DP does require the problem to actually have an MDP formulation.

In particular, the state must contain enough information for the
Markov property to hold:

P(s_next | history, a) = P(s_next | s, a)

In simple terms:

The current state must contain everything relevant for predicting
the future.

Tabular DP additionally becomes practical when the state/action spaces
are small enough to enumerate.

"Finite state space" is useful, but not the fundamental definition
of DP. Large or continuous spaces require other representations or
approximation methods.


WHAT DP DOES NOT ASSUME
-----------------------

DP does NOT inherently require:

- a manually written model
- a manually written policy
- a manually written reward function
- a finite physical environment
- a real environment to be running
- episodes
- a particular programming language
- a particular representation such as HashMap<State, f32>

These are implementation or problem-specific choices.


POLICY EVALUATION
-----------------

The following algorithm is iterative policy evaluation.

A policy pi is already given.

DP repeatedly applies the Bellman expectation equation:

V_(k+1)(s)

= sum_a pi(a | s)
    sum_s' P(s' | s, a)
        [R(s,a,s') + gamma V_k(s')]

Each iteration uses the previous value table to produce a better
estimate of the value of every state.

V_0 -> V_1 -> V_2 -> ... -> V

When the values stop changing significantly, the value function has
converged to the value of the given policy (under the usual assumptions).


POLICY EVALUATION IS NOT VALUE ITERATION
----------------------------------------

Policy evaluation asks:

"How good is THIS policy?"

Therefore it uses:

pi(a | s)

Value iteration asks:

"How good is the best possible choice from this state?"

Therefore it uses:

max_a

rather than averaging actions according to a supplied policy.


THE BIG PICTURE
---------------

Model-based DP:

            MDP MODEL
        S, A, P, R, gamma
            |
            v
        DP algorithm
            |
    +---------+---------+
    |                   |
    v                   v
V(s)                pi(a|s)

The important conceptual boundary is:

MODEL = description of how the world behaves

DP    = reasoning/planning procedure that uses that description

The model may be hand-designed or learned.
DP does not care where the model came from, as long as it is available
in the form required by the algorithm.
